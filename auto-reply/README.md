# 企微新消息监听 + IMA 知识库自动回复

## 1. 它做什么

```
企微收到新消息
  ↓ 约 1 秒
watcher.py 读 faswecom 本地库增量（仅私聊、非本人、非占位）
  ↓ 合并 5 秒内连续消息
responder.py
  ├─ IMA「客服知识库测试1.0」检索 + 取原文（MCP over HTTP）
  ├─ DeepSeek 按 Skill 规则判 AUTO / DRAFT / ESCALATE
  └─ AUTO 时经 faswecom MCP 发送并核对回执
  ↓
本地库出现带「（AI回复）」的本人消息 → 判定发送成功
```

单条消息实测耗时约 **7 秒**（知识库检索 0.7s + 模型 0.9s + 发送与入库核对约 5s）。

## 2. 文件

| 文件 | 说明 |
|---|---|
| `config.json` | 唯一配置：模式、监控范围、知识库、模型、通道 |
| `watcher.py` | 监听器：秒级轮询、幂等去重、发送核实、单实例互斥 |
| `responder.py` | 回复引擎：IMA 检索、模型决策、faswecom 发送 |
| `live-state.json` | 游标、已处理消息 ID、处理台账 |
| `events.jsonl` | 每轮结果流水 |
| `review-queue.jsonl` | 草稿、转人工、发送未核实的记录 |
| `kb-cache/` | 知识库原文缓存（默认 15 分钟） |
| `logs/watcher.log` | 常驻运行日志 |
| `start-watcher.ps1` | 前台启动 |
| `install-startup-task.ps1` | 注册登录自启计划任务并立即启动 |

## 3. 三种模式

| 模式 | 会发消息吗 | 用途 |
|---|---|---|
| `preview` | 不会 | 只验证消息能否被发现 |
| `dry_run` | 不会 | 验证知识库命中与回复质量 |
| `live` | AUTO 时会发 | 正式无人值守（当前配置） |

改 `config.json` 的 `mode` 后需重启监听器。

## 4. 启动与停止

```powershell
# 注册登录自启并立即启动（只需一次）
& '<AUTO_REPLY_DIR>\install-startup-task.ps1'

# 停止
Stop-ScheduledTask -TaskName 'WorkBuddy-WeCom-AutoReply'

# 前台调试（Ctrl+C 停止）
& '<AUTO_REPLY_DIR>\start-watcher.ps1'

# 单轮演练（跳过 5 秒合并窗口）
& 'G:\适配器\runtime\python.exe' -X utf8 -B watcher.py --config config.json --once --force-process
```

## 5. 防重复与安全边界

- 处理完的消息 ID 立即写入 `processed`（保留 3000 条），永不再回复。
- 发送成功不看接口返回，只看企微本地库是否出现带 `（AI回复）` 的本人消息；未出现记 `NOT_VERIFIED` 且不重发。
- 单实例：占用 127.0.0.1:45917，重复启动的第二个进程直接退出。
- 超过 30 分钟的旧消息（如断网恢复后的积压）直接丢弃，不补发。
- 高风险词（投诉、退款、赔偿、律师、密码、验证码等）在调模型前即拦截为 ESCALATE。
- 知识库置信度低于 0.8 时降级为 DRAFT，不发。

## 6. 常见故障

| 现象 | 排查 |
|---|---|
| 启动即退出，提示端口占用 | 已有实例在跑：`Stop-ScheduledTask` 后重试或结束 pythonw 进程 |
| `events.jsonl` 无新记录 | 确认企业微信与 faswecom 适配器在运行，`G:\适配器\data\chats.sqlite3` 有新增 |
| `infra_error: 无法连接` | faswecom 适配器或 IMA 掉线，检查对应服务后重启监听器 |
| `NOT_VERIFIED` | 发送接口成功但库里没落记录：确认适配器同步延迟，检查 `review-queue.jsonl` |
| 回复不准 | 补 IMA 知识库文档；相似问法越全命中越稳 |
| 想暂停某会话 | 加入 `config.json` 的 `blocked_conversations` 或 `blocked_names` |

## 8. 技能路由（v4）

知识库不再是终点。判定链改为五道闸门：

```
G0 红线关键词  → G1 IMA 知识库 → G2 技能语义路由 → G3 澄清 → G4 转人工
```

知识库有可直接对客的答案时，照旧答复并结束；知识库没有定论（未命中、只覆盖一部分、模型判 DRAFT）时，进入 G2 查技能注册表。

| 文件 | 作用 |
|---|---|
| `skills/registry.json` | 技能注册表：触发语义、反例、必需槽位、`kb_shadow`、兜底话术 |
| `skill_router.py` | 打分匹配、槽位收集与记忆、执行通道调用 |
| `slot-state.json` | 各会话待收集槽位（默认 30 分钟过期，自动清理） |
| `skill-queue.jsonl` | 执行通道为 `queue` 时的待办队列 |
| `logs/<时间>-<技能>.stdout.json` | 技能执行原始输出 |

### 槽位收集

命中 SKL-01 但客户没说签约人姓名时，先回话术索要，不查订单；客户回复的两到四个汉字视为姓名，直接带入技能；两次给不出则转人工。同一会话内已给过的姓名会复用，不重复追问。

### 执行通道

`config.json` → `skills.executor`：

| 值 | 行为 |
|---|---|
| `builtin`（当前默认） | 进程内直连 Doris（`km_order.py` + `vendor/pymysql`），毫秒级返回真实订单与物流 |
| `queue` | 命中技能后写入 `skill-queue.jsonl` 并回兜底话术，业务数据由人工消费 |
| `cli` | 拉起 WorkBuddy CLI 执行 skill，当前不可用（见下方限制） |

### 物流查询的三档结果

| 客户给的姓名 | 回复 |
|---|---|
| 精确匹配唯一门店 | 门店名称 + 近 90 天订单数 + 订单1~3（下单时间、状态、金额原值、物流公司、运单号、商品与数量），更多订单提示可续发 |
| 只有相近名称 | 列出候选门店与地址，请客户回序号；**不直接给数据**，防止查错门店 |
| 完全查不到 | 系统上暂时未查询到相关物流信息，请您检查签约人姓名是否有误 |
| 门店存在但无订单 | 说明该门店近 N 天没有商城订单记录 |

查询窗口由 `config.json` → `skills.order_days` 控制，默认 90 天；窗口内为空时自动回退查全部历史。

改完需重启监听器。

### 已知限制：CLI 通道当前不可用

实测 `node codebuddy.js --print ...` 在本机 90 秒无任何输出即超时（`--version` 正常返回 2.103.3，最小 MCP 配置同样卡住），说明阻塞点在 CLI 的会话初始化而不是 MCP。因此技能执行改为进程内直连（`builtin`），整条链路不再依赖 CLI。

数据库连接沿用 `~/.workbuddy/mcp.json` 里 `xlx_diros` 的账号，只读；驱动用 `vendor/pymysql`，不污染系统环境。

如果以后仍想走 CLI：
1. 单独跑一次 `codebuddy --print` 确认能在 30 秒内返回；
2. 把 `skills.executor` 改为 `cli`；
3. 用一条物流咨询验证 `logs/<时间>-<技能>.stdout.json` 出现且内容可解析。

## 9. 对话不中断的三条保障（v4.1）

客户最怕的不是答错，是发完消息没人理。以下三条专门防沉默。

| 场景 | 之前 | 现在 |
|---|---|---|
| 转人工（红线、无技能、低置信） | 内部标记 ESCALATE，客户收不到任何话 | 一定回一句转人工提示，`send_notice=true` 允许发送 |
| 客户把名字打错，查无此人 | 槽位状态被清空，客户再发正确姓名时无人应答 | 保留槽位状态，客户改个名字可直接重查 |
| 客户连续 3 次查无此人 | 无限循环 | 第 3 次自动转人工并带上「已转接」提示 |

配置项：`skills.slot_ttl_seconds`（默认 3600，客户一小时内补充姓名仍能接上）、`skills.notfound_max`（默认 3）。

实现要点：`responder.handle` 是对外入口，`_handle` 是原逻辑；入口统一给 ESCALATE 补兜底话术并调用 `finish_send`。`watcher` 的发送条件从“仅 AUTO”改为“AUTO 或 send_notice”。

### v4.2 补充：姓名识别的两个坑

1. **客户会在句子里带姓名**：`签约人姓名是何子君`、`我叫张三`、`门店叫张三`。新增 `extract_name()`，先按「签约人姓名 / 姓名 / 名字 / 叫」等标记切出尾部再取 2-4 字，最后才退回整句判定。
2. **客户不按套路回答**：展示门店候选后，客户可能报一个全新的姓名，而不是回序号。原逻辑只会反复提示「回复序号」，形成死循环。现在先尝试把这句话当姓名，换了人就立即重查；连续 2 次无法解析才转人工。

同时把「在吗 / 不知道 / 忘记了 / 算了」等口头语列入 `NON_NAME`，避免被当成姓名去查库。

### v4.3：寒暄与「人工」单独处理

之前所有无法归类的消息都走转人工，导致客户说「你好」也回「已转客服」，既不专业，也会把人工队列冲爆。

现在判定顺序里加了两道前置：

| 消息类型 | 判断方式 | 回复 |
|---|---|---|
| 明确要人工 | 命中 转人工/找人工/人工/真人/转接/找客服 | 「好的，已为您转接人工客服，请稍候」 |
| 寒暄问候 | 你好/您好/在吗/哈喽/早上好 等 | 一段能力菜单，提示可回复「人工」 |
| 感谢确认 | 谢谢/收到/好的/嗯/拜拜 等 | 「好的，有需要随时找我。」 |
| 带业务内容 | 「你好，帮我查快递」 | 不当寒暄，正常走知识库与技能 |

寒暄分支走 `AUTO` 发送，`review-queue.jsonl` 不再被「你好」「谢谢」刷屏。

### v4.4：话术定稿与转人工强规则

| 项 | 定稿 |
|---|---|
| 欢迎语 | 你好，我是客服助手，有什么问题呀~ |
| 冷却期内再次寒暄 | 在的，您说~（`skills.welcome_cooldown_seconds`，默认 600 秒） |
| 感谢/确认 | 好的，有需要随时找我。 |
| 要人工 / 解决不了 | 我帮您转接人工哈，您稍等一下，人工会与您联系的，谢谢~ |

转人工两条规则收紧：

1. **只有客户主动说**：人工、真人、人呢、真人呢、人工呢、客服、客服呢、人工客服、找人工、要人工，或句中出现「转人工 / 转接人工」，才判定要人工。「人工客服电话多少」这类问句不误判，正常走知识库。
2. **解决不了的一律用同一句**：`handle()` 入口把 ESCALATE 的 reply_text 统一覆盖为定稿话术，模型自拟的转交措辞不再外发，保证对客户口径一致。

新增状态文件 `welcome-state.json`，记录每个会话上次发菜单的时间，超过 24 小时自动清理。

### v4.5：DRAFT（部分覆盖）不再沉默

**问题**：客户问「美团提现多久到账、提现了还不到账」，知识库只覆盖了「什么时候到账」这条，模型判 `DRAFT`、置信度 0.72（低于 0.8），结果既不发送也不转人工，客户看到空白。

**根因**：发送条件只有 `AUTO`，`DRAFT` 既不走 `finish_send`，也不是 `ESCALATE`，落进了「什么都不做」的缝里。

**修复**：知识库命中但判定为 `DRAFT` 时，只要模型给出了可用答复且置信度 ≥ `draft_min_confidence`（默认 0.6），就带着答复发给客户，同时 `send_notice=true` 并进 `review-queue.jsonl` 供人工复核。低于 0.6 或没有答复文本，统一转人工。

判定顺序（知识库命中后）：

| 情形 | 处理 |
|---|---|
| AUTO 且置信度 ≥ 0.8 | 直接答复 |
| 有技能匹配 | 转技能 |
| DRAFT 且置信度 ≥ 0.6 且有文本 | 答复 + 进复核队列 |
| 其他（ESCALATE、低置信 DRAFT、空文本） | 转人工，用统一话术 |

## 10. 转人工通知（v5.0）

判定 ESCALATE 时，除了给客户回一句话，还会把客户信息与最近对话推给指定人工客服。

### 推送内容

| 字段 | 来源 |
|---|---|
| 客户显示名 | 本地库 messages.conversation（企微备注/昵称） |
| 外部联系人 ID | 本地库 messages.sender_id（企微 external_userid） |
| 触发原因 | 客户主动要人工 / 命中红线 / 知识库与技能都答不了 |
| 最近对话 | 本地库按 id 倒序取 20 条，含时间与双方身份 |
| 时间 | 推送时刻 |

**关于微信号**：企微本地库只存外部联系人 ID（如 788130XXXXX），**不存微信号（wxid）**。真要微信号，需要客户是微信好友且通讯录已同步，或让客户自报。当前用「显示名 + 外部联系人 ID」定位，唯一且够用。

### 配置

```json
"handoff": {
  "enabled": true,
  "agent_name": "人工客服的企微名称",
  "agent_recipient_id": "",
  "history_limit": 20,
  "cooldown_seconds": 300
}
```

`agent_name` 由 `search_wecom_recipients` 解析；也可直接填 `agent_recipient_id` 跳过解析。
`cooldown_seconds` 防止同一客户连续触发时刷屏，默认 5 分钟。

### 落盘

| 文件 | 内容 |
|---|---|
| `handoff-log.jsonl` | 每次推送的状态（SENT / FAILED / SKIPPED）与原因 |
| `handoff-state.json` | 各会话上次推送时间，冷却判断用 |

推送失败不影响给客户的回复——客户侧照常收到话术，只在日志里留痕。

### v5.1：人工客服已钉死 + 通道故障兜底

- 人工客服：`人工客服`（`agent_recipient_id=person-<人工客服ID>`），`enabled=true`。
- **发送通道当前不可用**：企微客户端已升到 5.0.13.6005，适配器 0.4.11 只适配 5.0.11.6029 / 5.0.12.6018，`send_wecom_message` 返回 `NOT_SENT`（note：未匹配已验证的原生接口，未调用发送接口）。这不只影响转人工通知——**所有客户回复同样发不出去**，events.jsonl 从 14:02 起全是 `NOT_VERIFIED`。
- 兜底：`state` 不在 SENT 集合时，通知全文落到 `handoff-inbox/YYYYMMDD-HHMMSS-客户名.txt`，客服可手工查看，保证转人工请求不丢。

修复方向（代码侧无法绕过）：
1. 升级 faswecom 到支持 5.0.13 的版本；或
2. 把企业微信降级回 5.0.12.6018，并关闭自动更新。

通道恢复判断标准：`events.jsonl` 里重新出现 `send_state=VERIFIED`，或 `handoff-log.jsonl` 出现 `state=SENT/VERIFIED`。

### v5.2：转人工推送的可靠性与催办（实测通过）

**人工客服收不到的真实原因**：15:34 那次推送回执是 `PENDING`，旧代码把 PENDING 当失败、只落盘不重试，消息永久卡住。同期客户侧回复已 `VERIFIED`，所以不是通道不通，是**状态判定与重试缺失**。

修复：

| 项 | 旧 | 新 |
|---|---|---|
| 成功判定 | 只认 SENT/VERIFIED | 增加 `SERVER_RECORDED`（适配器真实成功的状态） |
| PENDING | 直接判失败 | 轮询等终态，最多 `wait_seconds=8` |
| 失败 | 落盘后不再管 | 自动重试 `retries=2`，换幂等键避免被判重 |
| 重复转人工 | 5 分钟冷却一律拦掉 | 区分首次与催促：`reminder_interval_seconds=120` 内不重复，超时发【催办】，最多 `max_reminders=3` |
| 客户话术 | 无论是否送达都说“转接人工” | **先推送再答复**：送达成功才说「已为您转接人工客服，请稍等片刻」；未送达仍说「我帮您转接人工哈…」 |

实测：首次发送 `SERVER_RECORDED`；紧接着第二次跳过；间隔 130 秒后连发 3 次【催办】后自动停止；人工客服会话内确认收到 8 条测试消息。

### v6.0：人工客服双向闭环 + 工单摘要

**一、人工客服不再是“客户”**

新增 `handoff.agent_conversation_id`。watcher 收到该会话的消息时直接分流，不走知识库、不走技能、不回欢迎语：

```
客户说「转人工」
  → 推送工单给人工客服（OPEN）
  → 客户收到「已为您转接人工客服，请稍等片刻」
人工客服回「收到」（内容不限）
  → 系统识别为人工接单
  → 原客户收到「人工已经帮您转达了，请稍等片刻~」
  → 工单状态 OPEN → ACKED
```

没有待接单工单时，人工客服发消息只会记录 `agent_reply / NO_TICKET`，不会误发给任何客户。

**二、推送模板改为「摘要式」**

不再罗列 20 条原文，改为模型生成的问题摘要（`responder.summarize_conversation`，最多 120 字）：

```
【转人工】、K 需要人工跟进
客户：、K
外部联系人ID：788130XXXXX
触发原因：客户主动要人工
时间：2026-11-02 16:07
客户问题：客户询问美团提现到账时间及进度，称广州六元素店昨天下午五点提现后尚未到账。
         客服答复正常周期14天、特殊活动按特殊打款周期，需核实订单信息，并表示转接人工。
         客户多次要求转人工核查。
```

摘要生成失败时自动降级为「客户问题：最近对话如下」+ 原文，不会空白。

**三、状态文件**

| 文件 | 作用 |
|---|---|
| `handoff-tickets.json` | 客户 → 工单状态（OPEN/ACKED）、接单时间 |
| `handoff-state.json` | 催办节流 |
| `handoff-log.jsonl` | 每次推送与接单的状态流水 |
| `handoff-inbox/` | 发送失败时的全文落盘 |

### v6.1：发送配额是硬约束 + 结束语温柔收尾

**根因（今天三次“没回复”的共同原因）**：适配器返回
`本连接已达到发送/管理工具的每小时上限（20 次）；请稍后继续`
——不是逻辑问题，是 **每小时 20 条发送配额被打满**。16:17 起所有发送失败，包括客户答复与人工回执。

处理：
- watcher 识别该错误为 `rate_limited`，不再按 infra_error 重试 3 次（重试只会继续撞墙），直接放行并留档
- 配额属 faswecom 连接级限制，代码无法绕过；需在 faswecom 后台调整或控制发送量

**话术统一**：所有转人工场景，客户都看到
`当前问题我帮您转人工，请稍等片刻哈~`（送达、未送达、催办均同一句）

**结束语温柔收尾**（`responder.is_closing` + `gentle_reply`）：
- 判定：含 谢谢/感谢/好的/收到/嗯嗯/辛苦/拜拜 等，且整句 ≤8 字，且不含 但是/不过/还有/请问 等转折
- 处理：DeepSeek 生成一句 ≤40 字的温柔回应（temperature 0.8，max_tokens 300），并把工单 OPEN/ACKED → CLOSED
- 实测：「好的谢谢」→「不客气呀，有需要随时来找我就好。」；「好的，但是我还有个问题」不判结束语，正常走业务

### v6.2：打招呼不再被误判转人工

**问题**：客户发「你好，在吗」，系统回「当前问题我帮您转人工」，还建了一张工单推给人工客服。

**根因**：`is_social` 只做整句等值判断。`你好`、`在吗` 各自在白名单里，拼起来 `你好在吗` 不在，于是被判成业务问题 → 知识库未命中 → 无技能 → 转人工。

**修复**：`is_social` 增加组合判定 `_social_only()`——把整句按寒暄词从左往右剥，剥空即纯寒暄。单字词（好/行/早）不做起点剥离以外的前缀匹配，且整句超过 16 字直接不判寒暄，避免「好的退款怎么处理」被误判。

| 客户说 | 判定 | 回复 |
|---|---|---|
| 你好，在吗 / 在吗你好 / 你好在吗在不在 | 寒暄 | 菜单（或冷却内「在的，您说~」） |
| 你好，帮我看看货到哪了 | 业务 | 正常走知识库与技能 |
| 好的收到 / 嗯嗯收到 / 谢谢啦辛苦 | 致谢 | 好的，有需要随时找我。 |
| 好的，但是我还有个问题 | 业务 | 正常解答 |

**新增等待态**：该客户有未结工单（OPEN/ACKED）时，打招呼改回
`在的，人工正在帮您跟进，请稍等片刻哈~`，不再发能力菜单，也不重复转人工。

**顺带修掉「回复没发出去」**：17:06 那条答复的发送单停在 `PENDING`，旧代码只查一次状态就返回，被当成失败。现在 `send_reply` 遇到 PENDING 会轮询等终态（最长 10 秒）；watcher 采信适配器的成功状态（如 `SERVER_RECORDED`）而不只依赖本地聊天库同步，避免「其实发出去了」被记成 `NOT_VERIFIED`。

### v6.3：三句话分工 + 结束词扩充 + 推送模板精简

**一、转人工的客户话术按场景分开**

| 场景 | 客户看到 |
|---|---|
| 客户自己说「转人工」「帮我转一下人工」 | 好的，我帮您转接人工，请稍等片刻哈~ |
| 知识库与技能都答不了，系统主动转 | 当前问题我帮您转人工，请稍等片刻哈~ |
| 人工客服回任意内容确认接手 | 人工已经帮您传达了，请稍等片刻~ |

`wants_human` 的正则从 `转人工|转接人工` 放宽到 `转.{0,3}人工`，「帮我转一下人工」「转个人工」都能识别；「人工客服电话多少」这类问句仍不误判。

**二、结束词从 11 个扩到 29 个**

新增：结束、结束了、可以了、不用了、不需要了、知道了、明白了、了解了、没事了、没问题了、解决了、已解决、搞定、先这样、就这样、晚安、回头聊、谢啦、麻烦您了、行了。

配套调整：
- 长度上限 8 → 12 字（原先把「好的，那就这样吧再见」漏掉）
- 转折黑名单加「而且、问下、想问、哪里、帮我、麻烦帮我、能不能、可以帮」，防止「好的，帮我查一下退款」被误判成结束
- 单字「行」改为「行了」，避免「行不行」被判结束
- 「结束」这类两字收尾词现在会温柔回应并关单，不再掉进转人工

**三、推送给人工客服的模板**

去掉「外部联系人ID」一行；正文末尾固定附一句：

> 客户正在等着你哦，收到请回复任意内容即可，我帮您转发给客户，说明您已经接手

截断逻辑也改了：原先 `[:1900]` 会把末尾提示语切掉，现在先按 1900 减去提示语长度裁剪正文，提示语永远保留在最后。

### v6.4：转人工时客户收不到「好的」——根因是发送并发 + 幂等键复用

**现象**：客户说「帮我转个人工吧」，人工客服收到了工单，客户却一个字没收到；等人工客服回「好」之后，客户才收到「人工已经帮您传达了」。

**根因两条，都在发送层**：

1. **顺序**：旧逻辑先推人工客服、再回客户。两条发送间隔不到 2 秒，适配器要独占企微窗口，后一条会一直停在 `PENDING / 等待适配器接收请求`，客户侧永远等不到。
2. **幂等键复用**：`key = wecom-live-{messageId}-{timestamp}`。同一条客户消息若被重试，键不变，适配器直接把那条卡住的 PENDING 单原样返回——重试越多次，越不可能发出去。日志里 17:06、17:15、17:50 三条 PENDING 全是这个模式。

**修复**：

| 项 | 改法 |
|---|---|
| 发送顺序 | 先回客户，再推人工；两步之间 `handoff.send_gap_seconds`（默认 2.5 秒） |
| 幂等键 | 加进程内自增序号，同一消息每次发送键都不同 |
| 推送重试 | `retries` 2 → 0，避免往适配器队列里堆请求 |
| 客户兜底补发 | `NOT_VERIFIED` 后等 2 秒复查本地库，仍没有就用新键补发一次，记 `VERIFIED_RESEND` |

**话术再对齐**：

| 时刻 | 客户看到 |
|---|---|
| 客户要人工（即时） | 好的，这就帮您转达人工，请稍等片刻哈~ |
| 人工客服回复任意内容（已接手） | 人工已经受理，正在为您处理，请稍等片刻~ |
| 系统兜底转人工 | 当前问题我帮您转人工，请稍等片刻哈~ |

### v6.5：人工意图识别 + 转人工路径统一（被动=主动）

**一、「真人呢，没有真人吗」被当成"无法识别"**

旧规则只认整句等于「真人/人呢」或句中出现「转人工」。这类追问两句拼在一起，两条都不命中，于是走知识库 → 未命中 → 被动转人工，话术也和主动要人工不一样。

新增 `HUMAN_ASK`：句中出现 真人/人工/客服 且带 呢/吗/嘛/在不在/有没有/没有 就算要人工；同时用 `HUMAN_ASK_BLOCK`（电话/号码/收费/费用/多少钱/时间/几点/上班）排除打听信息类问法。

| 客户说 | 判定 |
|---|---|
| 真人呢，没有真人吗 / 有真人吗 / 人工在不在 | 要人工 |
| 人工客服电话多少 / 人工客服几点上班 | 不是要人工，正常查知识库 |

**二、主动与被动转人工走同一条路径**

| 时刻 | 客户看到 |
|---|---|
| 转人工（主动说 or 系统答不了） | 好的，现在帮您转接人工处理，请稍等片刻哈~ |
| 人工客服回复任意内容（接手） | 人工已经受理，稍后人工会与您联系，请注意查收~ |

`NOTICE_REPLY` 直接等于 `AGENT_REQUEST_REPLY`，不再分成两套措辞。

**三、人工客服收不到的真实原因：节流把新请求当成刷屏拦掉**

`_plan()` 只看时间窗：首次推送后无条件刷新 `last_reminder`，导致 120 秒内再转人工一律 `SKIPPED`。09:31 那次日志就是 `SKIPPED / 催办过于频繁或已达上限`——客户收到了「帮您转人工」，人工客服什么都没收到。

修复：`_plan()` 第一步先查工单状态，**没有未结工单就按新请求直接 send**；只有存在未结工单时才判断催办与节流。

已验证四种场景：全新 → send；有未结单+刚推送 → skip；有未结单+130 秒 → urge；工单已关后 2 分钟内再要人工 → **send**（修复点）。

### v6.6：物流查询后补发快递100指引

物流回复里出现真实运单号时，主消息发出后再补一条：

> 详细的物流信息您可以通过：微信小程序搜索快递100，根据发给您的运单号进行查询哦~

**触发条件**（`responder._has_waybill`）：回复文本中匹配 `运单号\s*([0-9A-Za-z]{6,})`。以下不补发：
- 索要签约人姓名
- 列出候选门店
- 「物流：未记录运单号」
- 门店近 90 天无订单

**实现**：`handle()` 在 `_handle()` 之后判断，命中则设 `followup_text` 并调 `_deliver_followup()` 发第二条；两条之间隔 `skills.followup_gap_seconds`（默认 1.5 秒），避免适配器把后一条挂起。补发失败只记 `followup_state`，不影响主回复。

**配额提醒**：一次物流查询由 1 条变 2 条发送，按每小时 20 条上限，等于每小时最多 10 次查询。

### v7.0：工单生命周期定为「接手即结束」+ 每 10 分钟催办

**一、人工接手 = 智能客服工单结束**

人工客服回任意内容后，系统给客户发「人工已经受理，稍后人工会与您联系，请注意查收~」，同时工单直接从 `OPEN` 置为 **`CLOSED`**（`close_reason=人工已接手`），不再停在 `ACKED`。

设计意图：从这一刻起是人工与客户的单线联系，智能客服的职责已履行完毕，不再参与判断。

**二、未接手则每 10 分钟催办，直到有人回复**

新增 `handoff.remind_pending()`，由 watcher 每 60 秒扫描一次，命中条件后发送【催办】：

| 条件 | 值 |
|---|---|
| 工单状态 | `OPEN`（未被接手） |
| 距上次提醒 | ≥ `reminder_interval_seconds`（默认 **600 秒**） |
| 提醒次数上限 | `max_reminders`（默认 **0 = 不限**） |

催办内容（简短，不重复 20 条对话）：
```
【催办·第N次】、K 还在等人工回复

已等待约 20 分钟
客户问题：客户询问美团提现到账时间

客户正在等着你哦，收到请回复任意内容即可，我帮您转发给客户，说明您已经接手
```

**三、`_plan()` 简化**

有未结工单时不再重复推完整工单（`skip`），催办统一交给定时器，避免同一件事推两遍。客户关单后再次要人工仍按新请求 `send`。

**配额影响（必须知晓）**：一个工单若长期没人接，每 10 分钟消耗 1 条发送额度，即 **6 条/小时**，占每小时 20 条的三成。若人工客服经常长时间不回复，需要放宽间隔或设 `max_reminders`。

### v7.1：同一工单最多提醒两次

一个工单只催两次，之后自动收口，不再反复打扰：

| 时序 | 动作 |
|---|---|
| t=0 | 转人工工单推给人工客服，工单 OPEN |
| t=10 分钟 | 第 1 次【提醒】、K 在等人工回复 |
| t=20 分钟 | 第 2 次【催办】、K 已等 N 分钟，仍没人接手，**发完立即 CLOSED** |
| 之后 | 不再发送；客户再要人工按新工单重新计数 |

参数：`handoff.max_reminders=2`、`handoff.reminder_interval_seconds=600`。`max_reminders=0` 表示不限次数（旧行为）。

实测：第 1 轮发 1 条（OPEN），第 2 轮发 1 条（CLOSED，原因「已提醒 2 次，人工仍未接手，自动结束」），第 3 轮 0 条。

**配额**：单张工单最多消耗 2 条提醒，加首次工单共 3 条，约占 20 条上限的 15%。
